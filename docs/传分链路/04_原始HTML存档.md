# 原始 HTML 存档

## 一、链路作用

**实施状态（2026-11-17）：调试存档与完整性校验已实现、实测通过。** `RawHtmlArchive` 逐页写入私有目录，提供大小限制、SHA-256、临时文件发布与失败清理；手机和平板两组共 160 份页面导出复核通过。本轮 manifest 属于调试记录，正式批次索引、账号归属、保留/删除策略及公开查询入口仍待实现，见 [实测记录](08_代理采集实测.md)。

把一次采集中取得的页面可靠留在本地。平台上传失败时可以直接补传；以后开发或修复 App 自用解析器时，可以重新解析存档，不必让用户重新进微信登录。

存档是成绩数据的来源记录，不是网络抓包日志。保存的是原始页面内容及理解它所必需的上下文。

## 二、架构规范

- `score/html` 唯一管理采集批次、页面内容及其索引；通过 `score` 公开入口保存和读取。
- `transfer` 只持有批次、页面的稳定引用，不自行推测存储路径或直接写入成绩目录。
- 页面模型自然归属 `score` 的公开边界，采集方提供数据；网络响应对象和数据库实体不得跨边界传播。
- `storage` 提供文件或数据库基础能力，覆盖、保留、清理策略由 `score` 决定。
- 原始页面不可被平台适配或本地解析原地修改。它的采集有效性、本地解析状态及平台上传状态分别归各自所有者维护。

## 三、如何实现

创建批次时记录游戏、请求采集范围、开始时间和任务关联。确认游戏身份后绑定稳定账号标识；未确认身份的批次明确隔离。

每个页面保存下列信息：页面 ID、批次 ID、语义页面类型、难度或分类、采集时间、编码、内容哈希、内容长度、采集器版本、有效性检查结果。来源使用不带敏感查询参数的页面标识，禁止保存完整授权 URL。已知的游戏版本可记录，未知则留空，不猜测。

文件保存使用同目录临时写入并在成功后原子发布，之后更新可查询索引；文件和索引不能做单事务时，要有启动恢复策略，识别孤立文件、缺失文件和未完成写入。只有确认内容可读且索引有效后，才向调用方返回成功。

下载响应解码后得到的 HTML 保持原样，以明确编码保存；同时记录来源编码。若将来需要保留字节级原始响应，应另行定义，不声称文本存档能还原压缩前后所有 HTTP 字节。

批次记录预期页面、成功页面及失败／取消项。部分采集失败也可保留有效页面，不把整个批次删除，也不将缺失页视为空成绩。

第一版存放在 App 私有目录，不自动对外共享。保留策略优先保证未完成上传和待解析批次不被自动清理；未来设定容量和历史保留上限时，由 `transfer` 经公开入口登记／释放必要的保留引用，避免 `score` 反向读取任务数据库。用户明确清理时要处理受影响的补传任务。

## 四、需要注意的地方

- HTML 本身可能含个人信息和隐藏字段，即使不额外保存 Cookie 也不是公开素材。导出和调试分享需单独脱敏。
- 本次采集账号与历史账号不同，应建立独立批次和归属，不覆盖当前账号的成绩来源。
- 存储不足或写入失败时，不能继续声称具备离线补传能力。第一版按“保存成功才上传该页”处理；已保存页面仍可保留。
- 页面引用要校验存在性及完整性，不能把清理或损坏后的文件当成成功上传的空内容。
- 验收覆盖写入中断、磁盘不足、索引发布失败、启动恢复、部分页面成功和不同账号隔离。脱敏样本应验证保存再读取内容一致。
