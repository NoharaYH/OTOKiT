# 微信回调捕获

## 一、链路作用

**实施状态（2026-11-17）：debug 链路实测通过。** 当前项目已实现 `NetCaptureProtocol`、`LoopbackCaptureProxy` 及 debug VPN 承载，在平板和手机收到与本轮游戏/state 匹配的微信回调。先处理首次 VPN 允许弹窗，确认通道就绪后才跳微信。正式 `transfer/runtime` 与任务公开入口仍待接入，具体证据和实验时序差异见 [实测记录](08_代理采集实测.md)。

让用户在微信中完成舞萌或中二的华立授权，并取得建立 NET 会话所需的一次性登录材料。这一段只负责把用户操作转换成可供后续登录使用的结果。

旧代码将华立授权链路的回调改为 HTTP，经本地 VPN 识别并截取回调 URL，再由爬虫完成登录。当前证据是“回调 URL 加后续 Cookie 会话”，不应预先把截获物命名为 access token。旧方案能否适用于当前微信与服务端，需要重新实测。

## 二、架构规范

- 逻辑归 `transfer/capture`，Android 服务运行承载归 `transfer/runtime`。
- 输入为任务标识、游戏及捕获配置；输出为一次性的登录材料，或拒绝、超时、取消、通道失败等结果。
- 捕获模块拥有临时监听资源及捕获状态，不拥有成绩、上传目标或查分器 Token。
- 只能向任务编排者交付结果，不能在隧道回调里直接启动爬虫或上传。
- 系统 VPN 授权弹窗由界面入口承接，任务协调器等待其明确结果；不能把“已请求授权”当作“VPN 已就绪”。

## 三、如何实现

1. 创建任务专属捕获会话，检查是否已有活动采集，准备有随机标识的入口。
2. 请求 VPN 使用权限；拒绝时结束准备，不复制入口也不跳微信。
3. 启动本地入口和捕获通道，等待可验证的就绪事件，再向 UI 提供复制链接和打开微信的操作信息。
4. 处理华立授权入口与回调，严格检查协议、主机、端口和路径；在协议允许范围内关联本次会话及已选游戏，不能凭任意包含 `callback` 的字符串触发登录。
5. 原子地接受第一次有效回调，拒绝重复交付；交给任务协调器后完成捕获阶段并释放资源。
6. 后续 NET 登录独立进行；若失败，由任务策略决定是否重新要求微信授权，不重放已经消费的回调。

优先验证仅接管微信的 VPN 配置，其他应用流量不进入捕获通道。必要的直连转发与 socket 保护集中在底层实现。双开／分身微信的包名和运行空间需另行实测，不默认单一包名覆盖所有场景。

HTTP 识别必须按实际接收到的字节范围处理，支持请求头跨多次读取，限制累计长度和等待时间。不能将整个 ByteBuffer 底层数组当作完整请求。使用明确的 URI 解析和目标白名单，不用宽泛域名后缀匹配代替校验。

通过事件确认资源已关闭，不沿用固定 sleep 三秒的时序。用户取消、超时、服务被撤销、重复启动和创建中途失败，都应走可重复调用的资源清理逻辑。

## 四、需要注意的地方

- 这一能力只针对用户主动发起的游戏登录。无需通用 HTTPS 解密、安装自签 CA 或关闭 TLS 校验；如果旧 HTTP 回调路径已不可用，应报告协议变化并重新评估。
- 不在日志中输出完整回调 URL、授权码或 Cookie；登录材料只在本次会话短期存在，不写入成绩存档。
- Android 同一用户空间的其他 VPN 可能与该功能冲突，应提供明确状态，不将连接问题误报成平台授权失效。
- 验收覆盖 TCP 分段、重复回调、错误主机、权限拒绝、用户取消、微信分身、VPN 撤销和端口占用；至少在真实微信和设备上验证一次完整登录交付。
- 旧代码参考：`OTOKiT-dart/android/app/src/main/java/com/noharayh/otokit/vpn/tunnel/HttpCapturerTunnel.java`、`server/HttpServer.java`、`crawler/CrawlerCaller.kt`。它们不是新版必须保留的接口。
- 参考：[Android VPN](https://developer.android.com/develop/connectivity/vpn)。
