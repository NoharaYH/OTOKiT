# 平台上传与补传

## 一、链路作用

**实施状态（2026-11-17）：待实现。** 本轮所有新旧项目对照均禁用真实平台上传；NET 页面已保存不代表水鱼或落雪已接收成绩。上传适配、返回值判定、失败补传及平台限流仍按下文实施。

把已保存的游戏页面上传到用户选择的水鱼、落雪账号，并分别记录结果。一家失败不否定另一家的成功，也不影响本地 HTML 已保存这一事实。

上传适配允许 HTML 和 JSON 两种路径。第一阶段以经验证的 HTML 接口为主，只有确实需要的特殊情况进行转换，不要求先完成 App 自用成绩 JSON。

## 二、架构规范

- 供应商请求与兼容处理归 `transfer/upload`，不放入 `auth` 或共用 `network`。
- 上传输入包含稳定页面引用、游戏、目标平台和目标账号身份；上传前通过 `score` 读取，通过 `auth` 获取对应授权。
- 供应商 DTO 仅在适配器内部使用，不作为本地用户成绩格式。
- 平台兼容转换不得修改存档，不能偷偷改变目标账号，也不能把普通 HTTP 成功直接等同于逐条成绩导入成功。
- 上传尝试与结果由 `transfer/task` 持久化；适配器返回结构化结果，不直接更新 View 或通过日志触发下一步。

## 三、如何实现

### 1. 建立上传计划

按目标平台支持的页面类型构建计划，区分必须的玩家资料步骤、成绩页面和不支持项目。第一版每个平台内部串行；两家可以独立调度，但要遵守各自限流。为避免初始复杂度，也可以先顺序执行两家，结果仍必须独立。

落雪需要先处理玩家资料的情况，必须显式表达依赖；前置失败后不要继续一串注定失败的请求。首次绑定游戏账号是否允许通过个人 OAuth HTML 接口完成，列为接入实测项，不从开发者接口行为推断。

### 2. 供应商适配

水鱼：按游戏调用 `maimaidxprober` 或 `chunithmprober` 的 HTML／JSON 更新接口，使用 OAuth Bearer 和对应写权限。舞萌 JSON 使用其规定的标题、谱面类型、`dxScore` 等字段；同名曲消歧和宴谱识别需验证。旧宴谱 Dart 转换、中二 WORLD'S END 修改 class 的补丁只能在当前样本证明必要后保留。

落雪：旧版调用 `user/maimai/player/html`、`user/chunithm/player/html`；公开文档仅列出部分个人接口，正式接入前需核实这两个路径的 OAuth 写权限、绑定和返回行为。不能直接换成需要开发者凭据的 `{friend_code}/html` 接口。普通谱面的 ID 与 standard／dx 类型、宴谱特殊 ID 分开转换；JSON 上传无法替代 HTML 的所有历史游玩时间语义。

共享的是发送基础能力和结果分类，不统一两家响应体。检查 HTTP 状态及平台业务字段，并区分成功无变化、明确失败、部分可识别变化和结果不确定。平台静默跳过无效记录时，不能对用户保证“所有条目已导入”。

### 3. 补传

记录页面引用、内容哈希、目标平台及账号、适配器版本、尝试次数和最近结果。补传只选择未成功项目，先确认原账号授权仍可用。

超时可能发生在服务端已提交之后，归类为结果不确定。只有确认具体端点的重复上传语义可接受后，才自动重试；最近游玩或历史记录尤其不能默认幂等。没有平台幂等键时，不声称实现端到端恰好一次。

429 按服务端提示或有限退避处理，网络故障有限重试；权限不足和页面不兼容不做盲目循环。取消后停止新上传并尝试取消当前请求，已提交的远端结果不能撤回。

## 四、需要注意的地方

- 采集游戏账号与平台绑定游戏账号应在接口能力允许时进行校验；无法验证时明确处理绑定流程，不能凭昵称相同认定为同一人。
- 平台账号重新授权成另一账号后，旧任务暂停，不自动向新账号补传。
- 旧版“抓了最近游玩但全部跳过”的行为不能照搬；分别确认平台支持程度。水鱼当前文档指出中二 2026 后最近游玩 HTML 导入无效果，应视为平台能力限制。
- 验收覆盖两家各自成功／失败、无变化、前置资料失败、授权过期、账号切换、429、超时不确定及特殊谱面。真实上传测试应使用用户明确指定的账号和数据。
