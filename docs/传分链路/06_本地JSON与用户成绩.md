# 本地 JSON 与用户成绩

## 一、链路作用

**实施状态（2026-11-17）：待实现。** 已取得可供开发解析器的真实 HTML 存档，但尚未生成 App 自用成绩 JSON、关联曲库、合并历史成绩或接入查询 UI；本轮仅完成来源页面的保留与校验。

将本地存档的官方页面转换为 OTOKiT 自己的结构化成绩，为成绩列表、统计和后续展示提供数据。此阶段可以在传分基础流程完成后实施，也可以在解析器升级后对历史存档重新运行。

本地用户成绩以公众号／NET 采集为来源，不靠从水鱼或落雪拉取成绩补齐。

## 二、架构规范

- 归 `score/json`，由 `score` 公开入口触发与查询。
- `score/html` 提供来源页面；需要识别曲目和谱面时调用 `musicData` 的公开查询能力。
- 解析、合并和发布策略由 `score` 唯一管理，页面和 `transfer` 不直接修改成绩记录。
- 本地 JSON 不采用任一供应商上传 DTO 作为永久格式，也不把供应商标题修正写成 App 内部曲目身份。
- 解析结果通过返回值或只读状态提供。`score` 不回调 `transfer` 实现，不自动发起网络上传。

## 三、如何实现

先定义最小且可版本化的本地格式，包含 `schemaVersion`、游戏账号身份、来源批次、采集时间、解析器版本和曲库关联版本。舞萌达成率与中二分数等游戏特有数据分别建模，不强行用大量可空字段装进一个通用记录。

谱面身份应包含游戏、曲目及谱面种类、难度或特殊谱标识。特殊谱、同名曲不能只用标题判断；无法确定的条目进入“待关联”结果，保留原文和来源，不能默认 Basic 或某个同名曲。

按页面类型与游戏选择解析器，先校验页面结构，再提取字段、关联曲库、进行范围与必需字段检查。识别失败与有效零条成绩必须区分，不能把失败转成 0 分记录。

维护两类含义不同的数据：本次采集快照及用于 App 查询的成绩视图。部分难度采集只更新对应范围，不删除未采集成绩；历史最佳成绩与最近游玩分别维护。具体字段是取最大值、按时间更新还是保留缺失，需要逐字段定义，不能整体拿“最新一行”覆盖所有成绩指标。

生成新结果时先构建和校验，成功后原子发布。解析器升级后可从原始存档重建，失败时保留上一份有效结果；页面缺失、曲库未就绪和解析不兼容分别报告。

## 四、需要注意的地方

- 本地解析失败不等于平台 HTML 上传失败，两项状态独立。第一阶段可以显示“原始页面已保存，自用成绩解析尚未接入”。
- 达成率精度、时区、FC／FS 标记、DX 分数和特殊谱类型需要明确格式，不能靠默认数值掩盖未知。
- HTML 不一定带完整曲目 ID 或游玩时间。不得猜测缺失字段，也不能把采集时间冒充游玩时间。
- 曲库未就绪时保留原始数据和待关联结果，不要求采集必须先完成整个曲库更新。
- 验收覆盖同名曲、宴谱、WORLD'S END、部分难度、空成绩、字段缺失、解析版本升级及不同游戏账号隔离。使用脱敏真实样本，验证重解析不会损坏已有有效成绩。
